### 0.2 기존 수치·기능의 보존 원칙 [유지]

- 기본 6등급(개척지0·촌락1·마을2·도시3·성채4·왕성5), 15종 자원, 24종 연구, 계절당 12일·1년 48일·10게임분/틱·144틱/일, 실제 이동·근무·교대, 8인 보호, 5능력치·12직업분야, 벌목 균등 분산, 전 타일 돌 기본 재고, 보호구역·습격·시장 재입고·위생·행복 산식 유지.

- 기존 일반 건설 대상 65종(CORE_BLD_1..65)에 신규 4종을 추가하므로 일반시설 69종, 영주관까지 포함한 CORE_BLD_COUNT = 70입니다. 도로/교량은 기존 enum 관례대로 시설 유형 집계에 포함되며, 이를 새 건축물 69채의 실제 존재 수로 오해하지 않습니다.

- 새 건물은 66=채토장, 67=급수탑, 68=천문대, 69=미술관 순으로 enum 끝에 추가합니다. '채토장이 채석장보다 앞'은 UI 분류 내 표시순서이지 채석장 등 기존 enum/세이브 ID를 재배열하라는 뜻이 아닙니다.

- 치료소·군영의 해금/건설비/유지비만 바꾸며 치료소 2×2·1명·지능 4 의료자격, 군영 5×3·6명·10시간 순찰·기존 강화 방어 수치는 유지합니다.

- 신규 건물의 생산·서비스는 실제 직원, 접근 가능한 도로, 근무, 원자적 자원 차감, 정밀 소수 잔여와 결합해야 합니다. UI만 변경해 실질 규칙이 바뀌지 않는 구현을 인정하지 않습니다.

- 이번 요청은 후반 승급 인구·연구·금화 조건 자체를 바꾸지 않습니다. 중간 성장 병목은 1.2.3 장기 QA로 별도 확인하고 임의로 완화하지 않습니다.

### 1.2 기존 플레이 세이브 [확정: 보호 / 제안 구현 결정]

이미 생성한 v1.2.2.2의 192×192 진행 세이브를 160×160으로 잘라내거나 강제로 축소하지 않습니다. 그렇게 하면 변두리 건물·탐사·자원·동물·습격 경로를 보존할 수 없기 때문입니다. v1.2.3으로 새로 만든 확장 월드만 160×160이며, 구세이브는 원래의 192×192 크기 그대로 로드하고 v1.2.3의 새로운 시설·거래·AI를 사용합니다.

- save_version: 10 → 11 [제안 구현 버전], 저장/로드 하위 호환. 공개 C 구조체 크기·ABI가 달라지는 경우 CORE_ABI_VERSION: 12 → 13 [제안 구현 버전]; 기존 이진 배포용 버퍼/공개 ABI 검사를 동반합니다.

- 구세이브의 지도·호수·광맥·점유·탐험·도로를 다시 생성하지 않습니다. 새로운 점토 매장량은 옛 맵의 바이옴과 호숫가를 기준으로 1회 결정론적 기본값 보정하고 이후 재적용하지 않습니다.

- 구세이브에서 구버전 치료소·군영은 철거하거나 환불하지 않습니다. 기존 완공 건물을 유지하되 신규 해금은 새로운 건설 명령에만 적용합니다. 미완공 군영도 기존 공사 진행률과 비용을 보존하고 공사 재개를 허용합니다.

- 기존 클래식 모드는 96×96 및 종전 클래식 상인·기본 규칙을 유지하며, 확장 상인을 클래식 세계에 두 번 생성하지 않습니다.

## 2. 바이옴 분산형 생성 [확정 방향/제안 알고리즘]

### 2.1 원인 분석 및 목표

현행 biome_at()은 4×4 고정 중심, 중심 간 48칸, 종류별 16개 시드 중 최근접을 고릅니다. 또한 191−x 반전과 축 교환이 들어가 실제로 같은 바이옴이 덩어리로 나오며 월드 축소와 충돌합니다. 1.2.3은 이 방식을 시드 기반 분산 패치 + 완만한 노이즈 워핑 + 수면 최종 분리로 대체합니다.

[확정] 초원 등 주요 바이옴은 한 곳에만 모이지 않고 2~3개 이상의 별도 지역에 나뉩니다. 희소 바이옴은 원래의 점유를 유지하면서 한두 개의 충분히 탐사할 만한 큰 덩어리로 둡니다. 즉, 한 칸짜리 색 점들이 무작위로 흩뿌려진 지도는 요구를 만족하지 않습니다.

### 2.3 생성 절차 [제안 구현]

- 160×160에서 바이옴별 목표 면적과 패치수 계산. 시드별로 서로 다른 방향의 중심 후보를 뽑되 격자 4×4 고정좌표 사용 금지.

- 같은 바이옴 시드는 서로 최소 24칸, 서로 다른 바이옴 중심도 최소 12칸 이격시키되 가장자리 예외는 허용. 난수는 코어의 저장 RNG 또는 별도 해시 스트림을 사용하고 재현 가능해야 합니다.

- 시드마다 비대칭 타원·방향성 및 멀티옥타브 좌표 워핑을 적용한 가중 보로노이/영역 성장. 가중 점수: D=(dx/a)^2+(dy/b)^2 + noise_bias; a/b는 각 종 면적 목표와 패치 목표에 맞춰 보정하고, 2~5칸 규모 경계 잡음을 겹칩니다.

- 동일 종 패치가 맞닿아 의도된 분산 패치들이 한 덩어리로 합쳐지면 해당 시드의 위치를 재추첨합니다. 1~3칸짜리 불필요한 섬은 인접 종으로 병합하며, 호수로 물을 채우기 전 육상 생물군계를 확정합니다.

- 시작 영주관 주변 12칸은 초원·숲이 중심인 안전 지형으로 부드럽게 블렌딩하며 산악·늪·절벽·수역으로 시작 진출을 봉쇄하지 않습니다.

- 바탕지형을 확정한 후 나무·광맥·호수 생성을 처리합니다. 호수로 잠긴 타일은 CORE_BIOME_LAKE가 되며, 주변 육상 바이옴 원본을 수온 판정용으로 따로 보존하거나 그 시점의 주변 육지 타일을 참조합니다.

- 맵 검사 패널·디버그 덤프에서 종별 면적·4연결 구성 수·평균 직경·시작 중심까지의 최단 이동거리를 출력합니다.

중반 탐사 품질 [QA/제안] 영주관 중심으로부터 실제 이동 가능한 거리 25~65칸 구간에 육상 바이옴 최소 6종을 관찰할 수 있는 시드 비율 90% 이상(산맥에 통로가 없는 시드는 실패). 6종은 생물군계 존재량을 바꾸는 새로운 업적/승급 조건이 아니라 QA 측정 기준입니다.

### 4.5 천문대: 1게임년 이내 사건 예측 및 연구 [확정 방향/제안값]

실제 연구·이벤트 코어를 사용합니다. UI 텍스트만 랜덤하게 '가뭄 예상'이라 표시하지 않습니다. 또한 예측 행위 때문에 원래 발생할 이벤트의 난수 순서가 달라져서는 안 됩니다.

- 규모: 왕성, 3×3, 정원4, 건설비·시간·유지비는 위 표. 4명이 모두 배치될 필요는 없지만, 근무 중인 직원이 최소 1명 있어야 예보가 갱신됩니다. 자격은 [제안] 실근무 직원 중 지능5 이상 1명이며, 미충족 시 연구·예측 유효성 0(예보 UI에 '유자격 연구원 없음' 표시).

- 근무: 예측/연구는 08:00~17:00 및 19:00~22:00 서비스로 구분할 수 있으며, 개인 근무는 기존 일일 XP·숙련 적립 최대9시간을 준수합니다. 실제 운영시간은 직무 분할근무 스케줄로 합법적으로 배정하고 하루 9시간 미만만 근무한 주민은 그만큼만 기여합니다.

- 연구: 정원4·정상 출석·평균 E=1을 표준으로 기준 4연구점/일, 산출은 연구점 = 4×F(기존 분야별 근무율 F, 무인0, 최대7.5 보정)에 맞춰 소수 잔여를 보존합니다. 기존 활성 연구 선택/전제·연구비/완료 이벤트를 그대로 따르며 무료 연구 즉시 완료 기능은 없음. 천문대 자체 연구에 마정석을 매일 소비하지는 않습니다(건설비로만 사용).

- 전망 기간: H=clamp(12+round(12×min(F,3)),12,48) 게임일, 여기서 F는 지난 1일 동안 실제 근무로 누적된 건물 기준 상대 유효 근무율입니다. 직원0 → H=0. 예: F=1.0이면 24일, F=2.0이면 36일, F=3.0 이상이면 48일(정확히 1게임년). 일단 작성된 전망은 다음 갱신까지 표시하지만 무근무 1일이 지속되면 오래된 예보임을 경고합니다.

- 대상: 실제 코드의 자연재해·풍년·가뭄·폭풍·전염병·교역 호황·한파·광산 붕괴와 같이 이벤트 발생 규칙이 존재하는 사건. 방어 습격의 기존 '사전 경보 없음' 원칙과 충돌하지 않도록 일반 습격의 정확한 사전 출현 시간·방향·세력은 예측 대상에서 제외합니다. 계절 교체는 원래 확정이므로 100% 일정 정보로만 나타냅니다.

## 7. 낚시터·항구의 수면 변 인접, 어선 애니메이션, 교량과의 관계 [확정]

### 7.1 변 인접을 배치·운영의 단일 규칙으로 사용

[현행 코드] 항구는 expansion_place_check()에서 물 인접 조건을 검사하고 생산에서도 1칸의 정확한 외곽 변을 탐색합니다. 반면 낚시터는 fish_request()에서 최대5칸의 수역을 탐색하므로 호수와 떨어진 육상에서도 어획 대상 수역이 발견될 수 있습니다. v1.2.3은 양쪽 모두 정확하게 호수 타일에 변으로 접해야 합니다.

정확한 정의: 시설 배치 범위 B=[x,x+w-1]×[y,y+h-1]의 네 변 중 적어도 하나가 4방향 이웃 관계로 CORE_TERRAIN_WATER이면서 water_id>0인 타일을 만나야 합니다. 대각선 접촉, 중간에 타일 하나가 끼어 있는 경우, 반경 5 안이라는 이유만으로는 불허입니다.

- 낚시터 2×2, 항구 3×3은 기존 면적·직원 수·비용·해금·수산 능력치와 공동 어획 상한을 유지합니다.

- 배치 미리보기부터 실제 배치까지 동일 함수 expansion_adjacent_water_id()를 사용하고, 인접 수역이 여러 개인 경우 실제 인접한 물타일 수가 많은 수역, 동수이면 수역 면적이 큰 곳, 그래도 동수이면 수역ID가 작은 곳을 선택합니다.

- 수면 타일에 직접 낚시터/항구 건물을 놓는 것이 아니라, 육상 건물 외곽이 수면과 붙는 것입니다. 건물 문 앞 육상 통행/연결도로 조건은 기존처럼 필요합니다.

- 항구 앞에 수면 교량이 있더라도 기반 지형이 물이면 물 인접으로 판정할 수 있으나, 어선 출항이 가능한 최소 한 타일의 교량 없는 수면 출항칸을 요구합니다. [제안] 부두가 완전히 다리로 막혀 있으면 배치 실패 출항 가능한 물길 없음, 이미 지은 항구는 건설 후 교량으로 막혀도 실제 식량 생산은 그대로 유지하고 어선의 시각 동작만 부두 앞 대기/짧은 순항으로 대체합니다. 이것은 '배가 교량을 통과하지 않되 생산 차이는 없다'는 요구를 우선하는 예외입니다.

- 실제 생산에서도 water_id가 없으면 0, 건설 이후 호수 지형이 사라지거나 주변 환경이 바뀌어 인접 수역이 0이면 어획0. 단순히 건물이 operating이기 때문에 식량이 생성되어서는 안 됩니다.

### 12.2 실제 지도 이동·대기·퇴장

상태는 DORMANT → SPAWN_WALK → TRADING_WAIT → DEPART_WALK → DORMANT, 경로 고장 시 REPATH_WAIT를 사용합니다.

- 등급1 이상에서 첫 예약을 생성하고 [제안] 첫 방문은 승급 후 4~8일(5가지 값 동일 확률20%), 그 뒤 방문부터 12~24일 간격으로 통일합니다. 승급 직후 구호품을 즉시 생성하지 않습니다.

- 160×160 또는 옛 192×192 실제 지도 변의 유효한 도로/육상 출현점을 검사합니다. 4면의 출현 가능 지점 개수에 따라 방향을 균등하게 분산하되 이동경로 없는 점은 다시 선택. [제안] 시작 8개 후보 → 최대 32개 후보 탐색.

- 출현점에서 대기지점까지 실제 A*/현재 주민 경로 기반 이동. 일차 경로가 끊기면 다른 진입점 재시도, 기존 이동 중 거짓으로 도착 처리 금지.

- 치료 진료가 완료되기 직전에 이번 환자의 실시간 상태를 읽고 필요량을 계산합니다. 실제 완치 트리거인 진료 시간 완료 + 서비스 크레딧 ≥1.0 + 약초 보유 ≥필요량이 모두 참일 때에만 한 번에 약초 전량 차감하고 치료 완료.

- 약초가 부족하면 해당 환자의 치료 진행을 유지/대기하되 완치·진료횟수 증가·서비스 크레딧 차감은 보류합니다. 3개가 필요한데 1개가 있다고 1개만 먹고 완치시키거나, 1개를 먼저 빼고 치료 실패시키지 않습니다.

- 수술 완료 틱에 다른 환자도 치료하면 환자 ID 순서 등의 결정론적 공정 순서로 한 명씩 처리해 같은 약초를 이중 소비하지 않습니다. 하루 제한과 실제 치료 인력의 근무를 유지합니다.

- 촌락 최초 치료소의 비용은 §4의 새 건설비로서, 추가 약초가 건설비에 이미 들어가는 경우 치료 소모량과는 별개입니다. 시작 약초 5개라면 치료소 건설에 약초2개를 쓴 뒤 정상 환자 1회(3개)를 치료할 수 있는 수준입니다([제안 비용 기준]). 그러므로 채집장 약초 생산과 장기 식량·약초 균형을 반드시 함께 QA합니다.

- 환자 프로필에는 필요 약초 3 / 보유2, 치료소 선택창에는 기본 3개/회 · 중증+1 · 유행병+1을 표시합니다. UI 숫자는 코어 계산 함수 expansion_heal_herbs_required(patient,clinic) 한 곳에서 구합니다.

### 14.1 육지에도 교량 설치 [확정]

현행 core/src/expansion_commands.c에서 type==CORE_BLD_BRIDGE ? terrain != WATER : terrain==WATER라는 조건은 교량이 물 위에서만 허용되게 합니다. v1.2.3은 평범한 보행 가능한 육지에도 교량 유형을 설치할 수 있도록 변경합니다. 물 위의 기존 교량은 그대로 유지합니다.

- 육상 교량: 바탕 지형을 변경하지 않고, 나무 판자 널빤지를 1×1씩 이은 통로로 렌더. 원형/막다른길/직각 회전·십자 교차를 자동 연결. 기존 교량의 길/이동 보너스·건설비·시간·유지비·도로 연결 요건을 별도 변경하지 않습니다.

- 수면 교량: 물타일의 terrain=WATER, water_id를 그대로 유지하고 타일 위에 선행 걸을 수 있는 교량 및 난간을 설치. 사람은 건널 수 있지만 어선은 그 타일에 들어가지 못합니다.

- 육상에서 교량을 놓을 수 있다고 모든 육지/건물을 통과할 수 있는 것은 아닙니다. 기존 건물 점유·성벽·문 차단·건설 중 도로 보호·건물 문 입구·습격 중 건설금지·지역 시야·비용 검사·지형 통행성 검사 유지. 자연 절벽·차단된 타일 등의 예외는 기존 walkable 정책을 따르며 억지로 통과시키지 않습니다.

- 수면 교량과 육상 교량은 동일 CORE_BLD_BRIDGE 건물 유형 및 기존 세이브 ID를 사용하되, 타일 렌더링 단계에서 기반 지형을 보아 WATER_BRIDGE/LAND_PLANK 아트를 선택합니다. 비용/작업량/소유자 번호를 중복 생성하지 않습니다.

### 14.2 난간은 단순 반복 타일이 아니라 4방향 자동 연결 [확정]

[확정] 수면 교량의 울타리/난간은 실제 주변 교량이 이어지는 방향을 보고 자동으로 생성·제거되어야 합니다. 한 줄로 수면 위 교량을 길게 놓으면 가운데 타일은 양 측면 2면에만 난간, 수면 한가운데서 다음 타일 없이 끊긴 끝은 진행축 반대와 두 옆의 3면 난간이 됩니다. 이어지는 교량을 건설하면 끝 난간은 즉시 열리고, 철거해 다시 끝이 되면 즉시 닫힙니다.

정확한 방향 정의: 각 물 위 교량 타일 p에서 N/E/S/W마다 connected[p][dir]을 계산합니다.

- 바로 옆 칸에 유효한 완공 교량이 있다면 해당 방향 연결됨. 공사중 교량은 안전을 위해 [제안] 시각 연결 미완공으로 보되, 최종 완공 후 바로 연결합니다.

- 바로 옆 칸이 육상이며 해당 육지 칸이 보행 가능한 도로·육상 판자·연결된 해안 접근칸이면 해당 방향을 육지로 나가는 개방 입구로 취급합니다. 해안 진입로를 난간으로 막아 보이지 않게 하기 위한 규칙입니다. 단, 육상 칸이 성벽/건물로 막혀 있으면 개방 입구가 아닙니다.

- 이웃이 그냥 물타일·없는 교량·막힌 지형·지도 밖이면 해당 방향은 노출된 물가이므로 난간을 그립니다.

제작량 산정 [제안 최소]: 방랑자 16걷기+8대기+1초상+1표식 = 26기본 프레임/리소스, 배 16선체 프레임 + 최대2인 분리 탑승 레이어, 교량 16수면 바닥+16난간+16육상 판자+4해안 접점=52방향 변형 자산(동일 베이스 이미지를 구성해서 최적화 가능), 신설4건물 × 최소 정면1 + 방향4 + 상태3= 최소 8요소/건물(실제 구성은 한 장의 시트 안에 다수 프레임을 포함). '48×4'는 기존 주민 48외형별로 192장을 통째로 다시 그리라는 뜻은 아니며, 기존 본체와 별도 탑승 레이어를 겹쳐 모든 192 조합이 정상 보이도록 하라는 최종 출력 요구입니다.

### 16.3 애니메이션·렌더 레이어·실제 트리거

- 수면 지형 → 물그림자/수면결 → 교량 바닥 → 난간 뒤쪽 → 주민/배 및 탑승 캐릭터 → 난간 앞쪽/해안접점 → VFX → UI/툴팁 순으로 깊이를 조정해 선체가 다리 위로 튀어나오거나 난간에 가려야 할 발이 보이는 현상을 막습니다.

- 상인은 SPAWN_WALK·TRADING_WAIT·DEPART_WALK의 실제 상태를 보고 걸음/대기 모션을 결정합니다. 영주관 옆에 도착하지 않았는데 먼저 대기 스프라이트나 거래 UI를 표시하지 않습니다.

- 어선은 실제 수면 경로 방향이 바뀔 때 동일 프레임에서 선체·탑승 직원·물결 방향을 모두 갱신. 출항/입항 시 직원 위치가 갑자기 두 배에 나타나지 않도록 기존 인원 상태를 유지합니다.

- 외형별 이미지/스프라이트는 필요한 모든 프레임을 실제 경로에서 로딩 성공해야 하며, 누락 시 자동 폴백 플레이스홀더로 QA를 속이지 않습니다. 로딩 실패 목록과 에셋 ID를 테스트에서 실패로 보고합니다.

### 17.3 세이브 v10→v11·ABI12→13 [제안 구현 번호]

- 저장 형식: SAVE_VERSION=11 [제안]. 로더는 v10의 고정 사이즈가 아니라 세이브 파일에 들어 있는 실제 지도 폭·높이를 기준으로 tile_count를 구합니다. 저장 체크섬/CRC/백업 보호원칙 유지. 새 필드가 없는 옛 파일은 명시된 기본값으로 채웁니다.

- C ABI: 공개 구조체나 CORE_BLD_COUNT 등이 바뀌면 CORE_ABI_VERSION=13 [제안]으로 갱신, raylib 게임 실행파일/코어 DLL/테스트의 동일 버전 매칭을 필수 조건으로 합니다. 기존 버전 실행파일로 신규 ABI 라이브러리를 무리하게 읽지 않습니다.

- 기존 건물: 구세이브의 치료소/군영이 옛 가격·옛 해금 등급으로 지어졌어도 그대로 존재합니다. 건설에 쓴 금화·재료를 환불·추징하지 않습니다. 신설 규칙은 새로운 건설 주문에만 적용. 연구·직원·급여·HP·시프트·보유량도 유지.

- 기존 지도: 192² 그대로 사용하고 호수/바이옴/광맥·나무·탐사·도로를 다시 시드로 생성하지 않습니다. 새 20호수·160지도·광맥 확산은 신규 월드 생성에만 적용됩니다.

- 기존 교량: 수상 교량은 새로운 자동 난간 마스크를 로드 후 주변에서 재계산하며, 원래 소유·HP·건설진도·연결도로/수로는 동일합니다.

- 기존 어업: 구세이브에 원래 지은 육상 낚시터가 물과 떨어져 있을 수 있습니다. [제안 호환 정책] 자동 철거·환불·시설 이동은 금지하고, 새 버전 로드 후 근처 수면 변 미인접 · 생산 중단 경고를 표시합니다. 이후 플레이어가 적절한 위치로 다시 건설해야 생산됩니다. 오래된 잘못된 생산물과 성장 기록은 소급 차감하지 않습니다.

- 기존 상인: 클래식 세계의 여행상인 저장 상태는 클래식 경로에 그대로 둡니다. 확장 세계는 새 필드가 없으면 최초 방문 예약부터 시작하며, 한 프레임에 클래식+확장 두 상인이 뜨지 않아야 합니다.
