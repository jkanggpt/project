# 2D 노멀 조명 실험 계획

현재 채택한 아트 방향은 [기존 픽셀 원화 조명 비교](PIXEL_LIGHTING.md)입니다. 사용자의 시각 검토에 따라 처음 만든 단순한 기하 표본 대신 기존 원화를 유지하고 작은 접지 음영·픽셀 표면 반응을 비교합니다. 아래 내용은 첫 기술 기준 표본의 구현·검증 기록입니다.

실험 브랜치는 `codex/lighting-prototype`입니다. 메인 화면과 튜토리얼이 병합된 기본 브랜치 `c979e73`에서 분리했습니다. 먼저 작은 조명 실험실을 만들고 결과를 판단합니다. 실제 게임의 규칙·저장·튜토리얼·지도 렌더러를 교체하지 않습니다.

## 표현과 좌표

현재 게임은 등각 다이아몬드 지도가 아닙니다. 16픽셀 정사각형 지면 위에, 위에서 내려다본 건물과 주민 그림을 발밑 기준으로 올리고 남쪽 발밑 순서로 정렬합니다. 주민 그림의 기준 높이는 24픽셀입니다.

실험은 이 표현을 유지하는 사영 `screen = (X, Y - Z)`를 씁니다. X는 화면 오른쪽, Y는 지면 남쪽, Z는 높이입니다. 지면은 정사각형을 유지하고 높이는 화면 위로 올라갑니다. 정밀한 카메라 보정값으로 주장하지 않으며 높이 계수는 실제 게임 그림에 맞춰 조정할 수 있습니다. 모든 광원·법선·그림자는 같은 월드 좌표로 계산합니다.

노멀 PNG의 RGB는 각각 월드 +X, +Y, +Z를 -1~1에서 0~1로 옮긴 값입니다. 바닥의 법선은 +Z이며 앞 벽의 법선은 +Y입니다. 일반 화면 방향 노멀을 그대로 바닥에 적용하지 않습니다. 노멀·높이는 선형 데이터, 알베도는 sRGB로 취급합니다.

## 먼저 만들 것

1. 균일한 무조명 재질 원화를 생성합니다. 잔디·포장돌·목재·기와·회벽·천·잎·물·흙을 포함합니다. 그림자와 광택을 원화에 넣지 않습니다.
2. 바닥, 물, 집, 지붕을 연 집, NPC, 나무, 바위, 상자, 토치, 벽을 대표하는 소수의 실험 스프라이트를 만듭니다. 실제 게임의 모든 그림을 변환하지 않습니다.
3. 재질을 간단한 모양에 입혀 오프라인에서 2D 스프라이트로 굽습니다. 같은 표면 교차점에서 알베도·노멀·높이·발광을 함께 생성해 픽셀 위치를 정확히 맞춥니다. 이 첫 표본은 색의 밝기를 깊이로 오인하지 않는 기하 기반 기준 표본입니다. 추가한 재질 세부 노멀은 image_gen으로 추정하고, 텍스처 오른쪽/위쪽 접선 축을 월드 표면 축으로 변환해 강도를 제한합니다. 기존 손그림 전체의 AI 노멀 품질을 검증한 것으로 주장하지 않습니다.
4. 실행 중에는 구운 2D 그림만 그립니다. 알베도, 노멀, 높이/발광의 화면 버퍼를 만들고 조명 셰이더로 합칩니다. 인물 좌우 반전 때 법선 X도 반전합니다.
5. 노멀은 표면의 밝고 어두운 방향을 만듭니다. 바닥에 드리우는 그림자는 별도의 차폐 모양과 광선 교차로 만듭니다. 해·토치·실내등 모두 같은 좌표와 차폐 데이터를 사용합니다. 창문과 문이 열린 벽은 구멍을 남겨 실내등이 벽 전체를 통과하지 않게 합니다. 높이 하나만 있는 지형으로 창문 구멍을 표현할 수 있다고 가정하지 않습니다.

## 비교와 조작

- 무조명 알베도 / 노멀 조명 / 노멀 조명과 그림자 / 노멀 표시 / 높이 표시를 전환합니다.
- 해의 방향·고도를 바꾸고 낮·석양·밤을 비교합니다.
- 토치와 실내등을 각각 켜고 끄며, 손전등 역할의 점광원을 이동합니다.
- 움직이는 NPC, 좌우 반전, 집과 벽 뒤의 바닥 그림자, 창문으로 나오는 실내등을 확인합니다.
- 창 크기와 화면 배율이 달라도 광원과 그림자가 월드 위치를 유지하는지 확인합니다.

## 아트와 변경 경계

원화는 `art/sources/lighting_lab`, 생성 요청은 `art/recipes/provenance.json`에 보존합니다. 실험용 출력도 제작·실행 매니페스트에 등록하고 기존 재생성·동일성 검사로 확인합니다. 생성 그림 권리는 CREDITS.md에 기록합니다. 실험 실행 파일은 별도 도구이며 기본 게임은 새 조명을 사용하지 않습니다.

코어, 저장, 콘솔, app.h, 튜토리얼 파일, 공용 진행·명세 문서와 CI 워크플로는 편집하지 않습니다. 별도 조명 도구·셰이더·아트 굽기 모듈과 해당 빌드 연결점만 추가합니다. 이번 요청에서는 원격 푸시나 PR 생성을 진행하지 않고 로컬 실험 결과를 먼저 제공합니다.

## 판단 기준

- 해와 점광원 방향을 바꾸면 맞는 지붕·벽·몸 표면이 밝아지는가.
- 바닥 그림자가 광원 반대 방향으로 생기고 낮은 해에서 길어지는가.
- 토치가 바닥·건물·NPC를 함께 밝히고 벽 뒤로 빛이 새지 않는가.
- 실내등은 창문·문을 통해 나오고 닫힌 벽·지붕에 막히는가.
- 발광 창문과 불꽃은 밤에도 보이며 낮밤 전환 때 원화에 반대쪽 그림자가 남지 않는가.
- 맵 정렬, 픽셀 필터, 좌우 반전, 확대가 법선·높이와 일치하는가.
- 실제 GPU 셰이더 실행 결과와 시간·해상도·테스트 장치를 기록한다. 소프트웨어 OpenGL 성능을 Windows GPU 성능으로 일반화하지 않는다.

## 결과

`castle_lighting_lab` 별도 실행 파일을 구현했습니다. 4×4 아틀라스의 16칸에는 잔디·포장돌·흙·물, 지붕 있는 집과 열린 집, 주민과 걷기 자세 3종, 나무·바위·상자·토치·벽·기준 구체가 있습니다. image_gen 재질 원화 2장으로부터 알베도, 월드 노멀, 높이/발광/거칠기 3장을 재현 가능하게 굽습니다. 실행 중에는 이 2D 아틀라스를 사용합니다.

방향광 1개와 점광원 4개를 구현했습니다. 토치는 시간에 따라 조금 흔들리고, 실내등 2개는 각 집의 창문·출입구로 나옵니다. 이동광은 지도를 드래그해 옮깁니다. 집·나무·상자·벽·주민의 차폐 모양이 바닥과 다른 물체에 그림자를 만듭니다. 걷기 자세와 좌우 반전에 맞춰 노멀·높이·차폐 모양도 바뀝니다.

### 실행과 조작

일반 개발 환경에서는 저장소 루트에서 다음 명령을 사용합니다. 그래픽 빌드에 필요한 X11/OpenGL 개발 패키지가 있어야 합니다. 이 실험은 실행 파일에 기록된 원본 저장소의 자산 경로를 쓰는 개발 도구이며 별도 배포 패키지를 만들지 않습니다.

```sh
cmake --preset linux-release -DCASTLE_WERROR=ON
cmake --build --preset linux-release
./build/linux-release/bin/castle_lighting_lab
```

이번 클라우드 빌드는 `/tmp/castle-deps/usr`에 준비한 개발 패키지 경로를 추가했습니다. 실제 구성·빌드·검사 로그는 `build/reports/lighting-prototype`에 있습니다. Windows에서는 `windows-msvc` 프리셋과 같은 `castle_lighting_lab` 타깃을 사용할 수 있으나 이번 실험에서 MSVC 실행 검증은 하지 않았습니다.

| 조작 | 결과 |
|---|---|
| 1 / 2 / 3 | 알베도 / 노멀 조명만 / 그림자 포함 |
| 4 / 5 / 6 | 월드 노멀 / 높이 / 차폐 표시 |
| 낮·석양·밤 버튼 | 광원과 환경광 사전 설정 |
| N | 낮과 밤 전환 |
| 좌우 화살표 / 상하 화살표 | 해의 방향 / 고도 |
| S / T / I / M | 해 / 토치 / 실내등 / 이동광 전환 |
| 지도 드래그 | 높이 24인 이동광의 월드 위치 변경 |
| P | 주민과 토치·물의 시간 흐름 정지 또는 재생 |

창 크기에 따라 지도 표시 영역을 확대합니다. 내부 조명 버퍼는 항상 512×384이며 실험 월드 영역은 256×192입니다. 따라서 큰 창의 결과가 더 넓은 지도나 더 높은 내부 조명 해상도의 성능 검증을 뜻하지 않습니다.

### 확인한 내용

Linux GCC Release와 `CASTLE_WERROR=ON`으로 전체 빌드가 통과했습니다. 전체 CTest 278개가 통과했고 `assets_runtime`, `assets_regenerate`, `assets_reproducible`, `lighting_geometry`, `lighting_maps`를 포함합니다. 등록된 실행 자산은 415개, 제작 입력은 331개입니다. 새 실험 자산은 3개, 새 제작 입력은 2개이며 두 매니페스트와 생성 요청 전문·SHA256·권리 고지를 기록했습니다.

실제 OpenGL 셰이더를 실행하고 화면의 특정 수신점 밝기를 읽었습니다. 아래 값은 화면 RGB의 가중 평균을 0~1로 정규화한 값이며 물리 조도 단위는 아닙니다.

| 검증 | 실제 화면 값 | 관찰 |
|---|---|---|
| 토치 바닥 그림자 | 차폐 끔 0.1584 → 켬 0.0502 | 벽 뒤 바닥에 그림자가 생김 |
| 실내등과 닫힌 벽 | 차폐 끔 0.1865 → 켬 0.0462 | 닫힌 벽을 통과하는 빛이 억제됨 |
| 실내등과 창문 | 열린 경로 0.3054 | 창문 경로로 빛이 나옴 |
| 구체 오른쪽 표면 | 동쪽 해 0.7423 / 서쪽 해 0.1090 | 월드 노멀에 맞는 면이 밝아짐 |
| 지면 +Z 법선 | 높은 해 0.6138 / 낮은 해 0.2306 | 지면이 수직 벽처럼 조명되지 않음 |
| 벽에서 떨어진 같은 바닥점 | 고도 75도: 0.5313 → 0.5313 / 고도 10도: 0.1965 → 0.0639 | 낮은 해의 그림자만 해당 지점까지 길어짐 |

1000×720, 1280×800, 1920×1080 창에서 셰이더 검사가 통과했습니다. 실제 데스크톱 창에서도 낮/밤, 노멀 표시, 인물 정지, 해의 방향·고도 변경, 이동광 드래그를 확인했습니다. 기존 게임의 `--smoke-test`, `--screenshot --screen tutorial|game`, 타이틀 800×600·1024×768·1440×900·1920×1080 캡처가 모두 종료 코드 0으로 통과했습니다. 이번 실험은 메뉴·저장·튜토리얼 전환 코드를 바꾸지 않았으며 해당 전환의 새 메모리 누수 검사를 주장하지 않습니다.

디스플레이 연결은 raylib 창 초기화보다 먼저 GLFW로 확인합니다. DISPLAY가 없거나 잘못된 경우 충돌 없이 종료 코드 1을 반환하는 것을 확인했습니다. 그래픽 창이 필요 없는 기하·자산 검사는 그대로 실행됩니다.

```sh
ctest --preset linux-release --output-on-failure
./build/linux-release/bin/castle_lighting_lab --check-geometry
./build/linux-release/bin/castle_lighting_lab --check-assets
./build/linux-release/bin/castle_lighting_lab --verify-render
./build/linux-release/bin/castle_lighting_lab --capture-dir build/reports/lighting-prototype/captures
./build/linux-release/bin/castle_lighting_lab --preset day --frames 90 --width 1280 --height 800
```

원격 클라우드의 Xvfb에서 그래픽 명령을 실행할 때는 `DISPLAY=:93`을 지정했습니다. 캡처 폴더에는 `albedo.png`, `day.png`, `day-normal-only.png`, `sunset.png`, `night.png`, `night-normal-only.png`, `normals.png`, `height.png`, `occlusion.png`가 있습니다.

### 성능과 남은 한계

검사 장치는 Mesa 25.0.7의 llvmpipe, LLVM 19.1.7 소프트웨어 OpenGL입니다. 1280×800 창에서 초기 10프레임을 제외한 80프레임의 렌더링·표시 벽시계 평균은 낮 57.53ms, 석양 47.56ms, 밤 33.36ms였습니다. FPS 제한을 끄고 각 경우를 순차 실행했습니다. GPU 전용 타이머 측정이 아니며 Windows 또는 실제 GPU 성능으로 일반화하지 않습니다.

현재 그림자는 선명한 경계의 그림자입니다. 최대 차폐 모양 64개와 점광원 4개를 순회하는 작은 장면용 구현이므로 전체 지도에 그대로 적용하기 전에 광원별·구역별 차폐 후보 제한, 정적 그림자 캐시, 내부 해상도 선택과 부드러운 그림자 비용을 검증해야 합니다. 주변광은 간단한 반구 근사이며 반사광이나 전역 조명은 계산하지 않습니다.

실험 그림은 간단한 기준 모양입니다. 생성 재질은 무조명을 요청했으나 색 디테일에 미세한 명암이 남을 수 있고 AI 세부 노멀은 측정 자료가 아닙니다. 실제 손그림에 적용할 때에는 각 그림의 무조명 색, 월드 노멀, 높이와 차폐 모양을 함께 검수해야 합니다. 노멀만으로 기존 그림의 높이·실루엣·창문 구멍을 복원할 수 있다고 가정하지 않습니다.

이 결과는 바닥 그림자·실내 차폐·표면 방향의 기술 가능성을 확인합니다. 다음 단계는 실제 화풍의 집·주민·나무 한 세트를 같은 사영으로 제작하고 실제 GPU에서 이동·애니메이션·부드러운 그림자 비용을 측정한 뒤, 게임 지도 렌더러 적용 범위를 결정하는 것입니다.

## 대화 안에서 조명 비교

일부 Codex 클라이언트에는 원격 Desktop 탭이 표시되지 않습니다. 이 경우 대화 안에서 직접 조작할 수 있는 고정 장면 비교 화면을 제공합니다. 인물·지형은 고정하고 해의 방향·고도, 낮·석양·밤, 토치·실내등·이동광, 알베도·노멀·높이·차폐 표시를 바꿉니다. 지도를 드래그하면 높이 24의 이동광을 옮깁니다.

`castle_lighting_lab --export-preview`는 실제 렌더링 버퍼와 같은 차폐 모양을 내보냅니다. 실행 조명과 내보내기는 `scene_occluders`를 공유하므로 별도의 건물·창문 모양을 다시 작성하지 않습니다. 브라우저 이미지 처리에서 데이터 알파가 변하지 않도록 높이 RGB와 거칠기를 각각 불투명 PNG로 나눕니다. 제작 자산을 바꾸는 작업이 아니라 고정 시점의 검사용 버퍼 출력입니다.

```sh
./build/linux-release/bin/castle_lighting_lab --export-preview build/reports/lighting-prototype/preview-data
python3 tools/lighting_lab/preview.py build/reports/lighting-prototype/preview-data /workspace/lighting-preview/lighting-test.html
```

`preview.py`는 장면 자료와 `lighting.fs`를 읽고, WebGL 정밀도 선언과 분리한 거칠기 샘플만 조정합니다. WebGL을 사용할 수 없으면 `preview-worker.js`가 같은 조명·광선 차폐 계산을 소프트웨어로 수행합니다. 자료는 화면 안에 포함하며 외부 API 호출이나 원격 컴퓨터 조작 권한이 필요하지 않습니다. 이번 출력은 약 515KB로 1MB보다 작습니다.

클라우드 브라우저에는 WebGL이 제공되지 않아 소프트웨어 경로로 검증했습니다. 실제 셰이더 검사와 같은 12가지 조명 설정의 13개 수신점을 비교했고, 화면 밝기 오차의 최댓값은 0.000049보다 작았습니다. 검증은 토치의 바닥 그림자, 닫힌 벽과 창문, 동·서쪽 해, 지면 법선과 해 고도에 따른 그림자 길이를 포함합니다. 이 브라우저에서 WebGL 경로를 실행 검증한 것으로 주장하지 않습니다.

내보내기를 추가한 뒤 경고를 오류로 처리한 실험실 빌드, `lighting_geometry`, `lighting_maps`, 네이티브 `--verify-render`가 다시 통과했습니다. 실제 대화 미리보기에서도 낮·밤, 노멀 표시, 태양 고도 변경, 이동광 드래그와 실내등 전환을 확인했습니다. 소프트웨어 화면은 입력이 바뀔 때 다시 계산하며 본래 게임의 실시간 GPU 성능을 측정하는 도구가 아닙니다. 네이티브 실험실의 애니메이션·게임 상태·카메라 이동은 이 고정 장면 화면에 포함하지 않습니다.
